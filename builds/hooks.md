# Hooks

The signatures the mod depends on are published as
[`api-surface.json`](api-surface.json), generated by `tools/QudGym.ApiProbe` from
the installed game's assembly. That report is metadata only: no method bodies, no
IL, and no game code executed. It says `runtime_hooks_verified: false`, which is
the honest part — it describes what the assembly *declares*, not what this mod has
*proved* at runtime.

What a signature list cannot carry is why each one is used, and what it looks like
when it is wrong. That is this file.

## The three shapes of blocking surface

Every way the game can stop and wait falls into one of three. They need different
treatment, and conflating them is most of what went wrong.

### A question — intercept the call

The game builds a list and blocks until something picks. Intercept the call,
publish the list, return an index.

| Hook | Used for |
| --- | --- |
| `Popup.ShowConversation` | Conversations. Returns the chosen option index. |
| `Popup.PickOption` | Every other menu — 80 call sites. Options in, index out. |
| `Popup.ShowYesNo` | Confirmation dialogs. Not currently gated. |

`PickOption` does **not** delegate to `ShowConversation`; it builds and waits on
its own, so the conversation hook does not cover it. It is the largest single win
in the mod: one hook retires 80 blocking menus.

### A notification — suppress it

The game says something and waits for a key, with nothing to decide. `Popup` has
a public `static bool Suppress` and every blocking method already honours it
identically:

```csharp
if (Suppress) { if (LogMessage) MessageQueue.AddPlayerMessage(Message, null, Capitalize); return Keys.Space; }
```

The gates raise that flag around the call. The game does its own logging, with its
own wording and markup handling, and nothing waits. `ShowBlock`, `ShowBlockPrompt`,
`ShowBlockSpace`, `ShowBlockWithCopy` and `ShowSpace` are all gated this way.

The flag is restored in a `Finalizer`, not a `Postfix`: a `Postfix` is skipped when
the original throws, which would leave notifications suppressed for the rest of the
session.

**The set has to stay complete.** Two of these were ungated for a long time and the
game sat on the embark summary — "It's you." with the character's equipment list —
which blocks during embark, before the harness ever gets a boundary. That is a
large part of why several early runs ended in `reset_required`: the game was not
failing, it was holding a dialog nobody could dismiss. `tests/test_api_surface.py`
fails if a hook is patched and not published, which is the cheap half of keeping
this list true.

### A browsable window — read the model

Nothing is being asked. `CmdInventory`, `CmdEquipment` and the journal push a
screen the player navigates. There is no call to intercept and no question to
publish, so the honest route is to read what the screen would draw.

The quest log is the worked example: `Game.Quests` minus `Game.FinishedQuests`,
formatted by `QuestLog.GetLinesForQuest` — the game's own formatter, including its
ordinal step ordering, its finished-step markers and its clipping. A caller sees
what a player sees rather than a summary that could disagree with the screen about
which steps are done.

## The gate cannot be a key

A popup cannot be dismissed by pushing the key it asks for:

```csharp
// TutorialManager
public static bool AllowPushKey(Keyboard.XRLKeyEvent ev, bool bAllowMap = false)
{
    if (instance != null && instance.ShowingPopup) return false;
    return true;
}
```

`Keyboard.PushKey` returns immediately when that is false, and it is false for
exactly as long as the dialog is up. **The refusal is silent**, which is why
pressing space against a live notification looked like a dead action rather than a
refused one.

This is the reason every approach here is a call the mod makes itself. Synthesising
input is unreachable by construction, not merely avoided.

## Gated narrowly, on purpose

`Popup.ShowBlock` has fourteen callers, and at least one is a real choice — the
Wishing well builds a maze and needs to be told which kind. A gate there would
silently delete a decision from the game to fix a quest notice.

So the quest notices are gated on the five named `Quest` methods instead:
`ShowStartPopup`, `ShowFailPopup`, `ShowFailStepPopup`, `ShowFinishPopup`,
`ShowFinishStepPopup`. One named method per notice, and every popup that needs an
answer is untouched.

## Reflection targets

Read through reflection, so a dependency the report cannot show. Each of these
cost a wrong answer first.

| Target | Reads | The trap |
| --- | --- | --- |
| `XRL.XRLGame.Quests` | Active quests | A **field**, not a property. |
| `XRL.World.Quest.ID` | Quest identity | Also a field. |
| `XRL.Collections.StringMap<T>` | The maps above | Backing array, `Count` + int indexer. |
| `XRL.World.Anatomy.BodyPart.GetOrdinalName` | Slot names | Returns markup. |
| `ConsoleLib.Console.Markup.Strip` | Clean names | `Transform` is *not* the same operation. |
| `ConsoleLib.Console.Markup.Transform` | — | Renders. Kept in the report so the difference is visible. |
| `XRL.UI.QuestLog.GetLinesForQuest` | Quest text | Four parameters, all optional. |
| `XRL.World.Parts.Inventory` | Carried items | Four overloads, split return-vs-out. |
| `XRL.World.Parts.Body.GetParts` | The player's anatomy | Four overloads; two return void. |

Two lessons, both paid for repeatedly:

**A reflection call returning `null` is a question, not an answer.** `StringMap`
declares `IDictionary<string, T>` but enumerates through a struct enumerator, so
`foreach` yields nothing and the read comes back *confidently empty* while a quest
is genuinely held. The map was never empty. The test was.

**`XRLGame.Quests` and `Quest.ID` are fields.** Reading either through the property
API finds nothing, silently, and the same mistake was made twice.

## A patch that does not bind takes the whole mod with it

Qud calls `Harmony.PatchAll` **once per mod assembly**, and the call is
all-or-nothing. A single mistyped parameter list — one `typeof(bool)` too many for
an eight-parameter method — aborted the call, so *no* patch in the assembly was
applied, including the embark gate. The game sat at the main menu.

The only symptom was one line in the game's own log:

```
MODERROR [QudGym] - Undefined target method for patch method
  static Boolean NotificationBlockSpaceGate::Prefix(String, String)
```

which is a long way from "the mod is dead". Two things prevent a repeat:

- `scripts/check_patch_bindings.py` resolves every declared target against the
  installed assemblies the way `PatchClassProcessor` does, and fails on any that
  does not bind.
- `scripts/deploy_mod.sh` verifies the patch types are present in the assembly it
  shipped. An entire session of patches once compiled, bound, passed every test,
  and did nothing, because the assembly was never deployed — every signal was about
  a file the game never read.

A binding check that runs against a *locally built* assembly is worthless, so it
reads the deployed one and refuses when there is nothing to read.

## Threads

`ConversationUI.HaveConversation` is synchronous. The conversation blocks the game
turn thread, which reaches the popup hook, which waits for an answer. The only way
to deliver one is the transport thread's `answer` op — and the game turn thread is
the thread that would deliver it.

Waiting there is a deadlock with a 120-second fuse. The symptom read as a
conversation that never started:

```
talk: prompt answer timed out
talk: AttemptConversation returned True
talk: no conversation started for watervine farmer
```

It started, ran, published three options and finished; the fallthrough then began
a *second* one. `talk:` is now staged and not awaited, and a plan's `options` step
is taken from inside the prompt, on the thread already waiting for it.

## Why `options` takes positions

A conversation's wording is the game's, and the game varies it between runs. The
same node has been offered as *"I'm looking for work."*, *"Do you have work that
needs doing?"* and *"My services are available if you have work to offer."*

A selector that matched on text therefore broke on ordinary variation, and each
break was patched. Positions cannot drift:

```
options 3, 1, 2, esc
```

`esc` is the game's own escape, index 0, offered only when it permits one — so
naming it on a conversation that forbids escape names a step the world does not
offer, and is reported rather than pressed.

## Regenerating

The probe takes the assembly, the hash it must have, and the report to write. Set
`QUDM` to the game's `Managed` directory:

```sh
export QUD_MANAGED=/path/to/Caves of Qud/CoQ.app/Contents/Resources/Data/Managed
dotnet run --project tools/QudGym.ApiProbe -c Release -- \
  "$QUD_MANAGED/Assembly-CSharp.dll" \
  "$(shasum -a 256 "$QUD_MANAGED/Assembly-CSharp.dll" | cut -d' ' -f1)" \
  builds/api-surface.json
```

The hash is required, and the probe refuses a mismatch rather than reporting on an
assembly it cannot identify — so a report always names the build it describes.

`tests/test_api_surface.py` fails when the report stops describing the code, when
a patched type is missing from it, when a reflected type is missing, when a local
path appears in it, or when it mixes assembly versions.

## The quest's travel step is not a walk

*What's Eating the Watervine?* asks for "two parasangs north of Joppa to Red
Rock". That is not `goto`, and not `CmdMoveToPointOfInterest` either.

- `CmdMoveToPointOfInterest` is for *nearby* named creatures and player-marked
  objects. It reads `GetPointsOfInterestEvent.GetFor(The.Player)`, which admits a
  cell only when it is `Explored` and holds a proper-named creature or something
  the player marked important. Red Rock is neither, so it is not in that list.
- There is no `MapScreen` or `WorldMap` class in the assembly. The only map
  classes are `Overlay.MapEditor`, which is a development overlay.
- Zone travel is therefore by **stairs**: `GameObject` tests
  `HasObjectWithPart("StairsUp")` / `"StairsDown"` and compares
  `parentZone.Z` against `currentZone.Z`. The zone level is `Z`, so "north" in the
  quest's terms is a `Z` delta, and the world is walked rather than fast-travelled.

So the missing primitive is a **zone transition by stairs**, and it is a fourth
kind of surface, distinct from the three already handled:

1. a question — intercept the call, publish the options, return an index
2. a notification — `Popup.Suppress`
3. a browsable window — read the model it would draw
4. **a world transition** — the game's own stairs action, which rebuilds the zone

The fourth has no interception point to hook and no model to read ahead of it. It
has to be driven the way a player drives it, through the object's own action, and
observed afterwards by what the new zone publishes. That is a materially different
mechanism from anything in the harness today, which is why `goto` naming a
distant place cannot work and must not be made to.

## Trade and looting both go through two blocking surfaces

Neither exists in the harness yet, and both were found by reading the game's own
trade path rather than by trying it.

### `Popup.ShowYesNo` — gated now

`XRL.UI.TradeUI.ShowTradeScreen` will not begin a trade until the water debt is
settled, and it asks with `Popup.ShowYesNo` first. That method was only
*observed*, never gated, so it blocked: a trade could not start. It is a question
with exactly two answers, so it is now answered through `MenuTurn` — the same
publication, escape rule and default a menu already uses — and the game's
`callback` is invoked so a caller that reads the callback rather than the return
value still gets its result.

This is not trade-specific. `PickItem` raises `ShowYesNo` for the weight limit
when taking a stack, so looting hit the same wall.

### `XRL.UI.PickItem.ShowPicker` — the container and inventory surface

Both `g` on a chest and the inventory go through
`PickItem.ShowPicker(IList<GameObject> Items, ...)`, which returns the chosen
`GameObject`. It is a screen with its own input loop, and it is the third shape —
a browsable window — except that it *returns* a selection, so it can be gated the
way `PickOption` is rather than read ahead of.

Two overloads exist, differing by a `ref bool RequestInterfaceExit`; the container
path uses the one without it. Gating this needs care because it is also reached
from equipping, trading and dropping, so a gate that assumes "a chest" would
change unrelated behaviour. `ShowContext` and `PickItemDialogStyle` are what
distinguish the call sites, and neither has been checked yet.

Not implemented. Recorded so the next attempt starts from the overload and the
style rather than from `take:` failing against a blocked screen.
